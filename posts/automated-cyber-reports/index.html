Turning attack traffic into reports

This happened a while ago, but I’ve always wanted to go through some of what happened in a little bit more detail rather than just giving bits and pieces in DMs, just never really had the time or the motivation to actually write something up myself for it, so I’m taking the opportunity to do that now.

I’ve maintained servers for a while now and I know enough to be able to and to know when to “set and forget” certain services, especially if it’s just some simple website, chances are we can run a very slim setup and we can mostly run completely “hands-free”. Lots of automated systems had already basically covered a lot of the surface area for attacks across a lot of the usual vectors, automated patch installation can help the vulnerability side and log auditing helps to identify suspicious activity, for example.

Still, even with this “set and forget” approach, it’s still wise to keep tabs on what’s happening on your box. After all, it is literally a computer connected to the Internet, so exploitation of it is something we need to actively mitigate and protect against.. and no system is ever fully secure, at least not in this current world that we’re living in. For my example, this box was just a dumb webserver, it didn’t really do much dynamic rendering or have some bespoke backend that needed intense workflows to get things done, I could mostly just design and implement things the way I wanted to.

At some point, during my regular checks over some of the server logs, I started to notice this really weird, annoying access pattern from lots of different IPs that all seemed to be trying to access a page that (1) didn’t exist, and (2) was actually intended to be reached by a consumer, retail Wi-Fi router, not my web server…

These logs show an HTTP request attempting to exploit CVE-2023-1389, a vulnerability in the TP-Link Archer AX21. It targets the router’s /cgi-bin/luci/;stok=/locale endpoint, where the country parameter was vulnerable to command injection.

At first, I was mostly researching up on the details of the vulnerability as there was not much needed to do on my side, we were not vulnerable because we were just a simple web server (there were no routers nearby!), but after getting annoyed by seeing them a few times, I started to get an idea..

Since the threat actors were indiscriminately targeting as many hosts as possible, without checking if those hosts were vulnerable or not, their requests are refused by the web server because the page(s) they are looking for simply don’t exist. Our logs show the attempt, but the threat actor gained basically nothing in the process. Us, on the other hand, we now know (1) where attacks are being sent from and (2) where requests for the payload would be sent to.

Their setup is assumed to be something like this:

  1. Threat Actor sets up some server that sprays as many hosts as possible
  2. TA sets up payload hosting on a different server
  3. TA has the server from (1) spray hosts by using rotated hosts provided to them by step 2.
  4. ????

Each attempt shows the IP of the box that is hosting the exploit payload, while the HTTP request leaks the box which sent the request out.

With this knowledge at hand, I had an idea to set up a fake page that was located at the exact location that the TA expected to exist, and to then capture the request IP, filter out the request itself, validate that this was in fact an exploitation attempt, and then log, and notify me when there were about 10-20 of them that I hadn’t yet reviewed. I manually reviewed the first batch of 2, 5, 10 and 20 attempts and then wrote up a script which automated the entire process for me.

The implementation is really basic, and in some ways, it’s pretty amateur, but that is all that’s needed for some things. I don’t really run this setup anymore, and I wouldn’t advise to use this script either for yourself, especially without looking at proper alternatives first.

I’ve omitted the urlhaus.py script, since it mostly contains other checks that are unrelated to this, but it essentially hashed a bunch of previous (normalised) request text and compared them to the one received, without including the host/IP/ports within it. This allowed me to check that requests matched known exploitation patterns before automatically reporting the extracted URLs.

Each attack is logged and I get notifications directly when they are received, skipping the usual logs that I’d audit regularly. But more importantly, we are now reporting directly to URLhaus when we receive them. These reports can help protect users as their blocklists are trusted and used by professionals across the industry.

URLhaus is an amazing resource and it really is one of the best community-driven projects that exists even today. I highly recommend finding some way to do something similar, providing that you can do so safely, because doing so will not just potentially protect your visitors/users/clients/customers, but it will also help protect the wider Internet too, and this is something that is important, especially as the Internet continues to grow.

This allowed me to contribute to URLhaus much faster and with much better information regarding the attempted attacks we were receiving. There are many other methods for setting up similar things like honeypots, but this is just one random idea that I had and wanted to use as an excuse to research more into these attacks etc. In the end, I had inserted over 650+ individual hosts and spreaders!
